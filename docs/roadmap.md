# NekoLang Roadmap

## 目标

NekoLang 是一个编译器项目。

- 输入：`.neko` 源程序
- 输出：二进制可执行文件
- 后端路线：**自研 ARM64 后端（主力）** + LLVM IR 后端（跨平台 fallback）

本路线图只围绕”把语言编译成可执行程序”展开，不引入解释执行路线。

## 当前状态

当前仓库已经具备这些能力：

- 词法分析、语法分析、AST 构建
- 符号表与四元式生成
- 基本语句：变量声明、赋值、条件、循环、输出、返回
- 一维数组声明、赋值、输出
- 函数定义、函数调用、作用域与返回值检查
- `bool` 类型与比较表达式
- 命令行参数读取与基础文件读写
- LLVM IR 生成
- 通过 `clang` 与 `runtime/runtime.c` 链接为可执行文件
- `check`、`build`、`run`、`llvm-ir` 等统一 CLI 命令入口

当前仍然存在的主要限制：

- 多文件构建和项目清单还未开始
- 运行时接口仍以基础标量类型为主
- 发布说明、平台说明和安装体验还不完整

## 工具链路线

NekoLang 包含两个命令行工具：

- **`neko`** — 编译器本身，操作单个源文件：`neko build main.neko`
- **`nekgo`** — 项目管理工具（类 `cargo`），操作项目目录：`nekgo build`

实现顺序分层推进。

### 第一层：编译器前端 CLI

先提供统一的编译器命令入口，服务单文件或少量源文件的构建流程。

建议命令：

- `neko check main.neko`
- `neko build main.neko -o app`
- `neko run main.neko`
- `neko llvm-ir main.neko`
- `neko ast main.neko`

这一层的目标是统一编译器使用体验，而不是立即引入项目管理和依赖管理。

### 第二层：项目工具

在语言核心和编译链稳定后，再引入类似 `cargo` 的项目工具能力。

建议命令：

- `nekgo new hello`
- `nekgo init`
- `nekgo build`
- `nekgo run`
- `nekgo test`
- `nekgo clean`

这一层将引入：

- 项目目录约定
- 项目清单文件，例如 `Neko.toml`
- 多文件构建
- 构建模式，例如 `debug` 和 `release`
- 标准库和运行时的链接策略

### 第三层：完整工程化能力

当项目工具稳定后，再考虑更完整的工程能力：

- 文档生成
- 示例模板
- 发布流程
- 依赖管理

依赖管理不应早于项目清单和多文件构建，否则返工成本会很高。

## Phase 1: 冻结 v0.1 语言核心

目标：稳定语法、固定边界，避免开发过程中频繁漂移。

任务：

- 固定标准关键字与兼容别名策略
- 固定 v0.1 支持的数据类型和语句集合
- 明确不在 v0.1 内的特性
- 让 README、文法文档、测试用例保持一致

完成标准：

- 文档与实现对齐
- 新增功能不再反复改词法和主语法

## Phase 2: 完整函数能力

目标：让程序可以被拆分成可复用的函数，而不是只能把逻辑堆在 `begin` 块里。

任务：

- 设计并实现 `return`
- 完成函数参数与返回值的语义检查
- 完成函数作用域与局部变量规则
- 补全 LLVM 后端中的函数定义与调用
- 增加函数相关的端到端测试

完成标准：

- 函数在前端和 LLVM 后端都能完整工作
- 能写并编译多函数程序

当前状态：已完成

## Phase 3: 完善类型系统与语义检查

目标：提高程序表达能力，并让编译错误更早、更明确地暴露。

任务：

- 增加 `bool`
- 明确比较表达式和条件表达式的类型规则
- 完善数组元素类型检查
- 补充参数数量错误、类型不匹配、重复声明等错误信息
- 统一前端语义检查和后端可生成能力

完成标准：

- 类型错误能在语义分析阶段被稳定识别
- LLVM 后端不会因为前端放过了非法程序而崩溃

当前状态：基础部分已完成，后续仍可继续细化错误提示

## Phase 4: 可执行程序所需的运行时能力

目标：让 NekoLang 能写出真正有用的小工具程序。

任务：

- 支持命令行参数
- 支持基础文件读写
- 扩展 `runtime/runtime.c`，将通用运行时能力收敛到 C 层
- 明确运行时接口与对应的 LLVM 声明方式
- 增加使用文件和参数的示例程序

完成标准：

- 能写一个读文件、处理内容并输出结果的命令行工具
- 能写一个依赖命令行参数工作的可执行程序

当前状态：已完成基础版本

## Phase 5: 发布与工程化

目标：让项目具备稳定构建、演示和发布能力。

任务：

- 提供统一 CLI 体验，例如 `check`、`build`
- 将现有 `neko.py` 演进为稳定的命令入口
- 去掉写死的目标平台配置，改为合理推导或配置
- 完善依赖检查和错误提示
- 提供若干完整 demo
- 补充发布说明与平台限制说明

完成标准：

- 新用户按照 README 可以编译并运行示例
- 能稳定产出二进制可执行文件

当前状态：CLI 入口与目标平台推导已完成，发布说明仍待补齐

## Phase 6: 项目工具

目标：让 NekoLang 拥有类似 `cargo` 的项目级工作流。

任务：

- 设计项目目录结构
- 设计并实现 `Neko.toml`
- 支持 `nekgo new`、`nekgo init`
- 支持项目级 `build`、`run`、`test`
- 支持多文件编译与链接

完成标准：

- 用户可以创建、构建并运行一个标准 NekoLang 项目
- 项目工具不要求用户手工组织底层编译命令

## Phase 7: 自研 ARM64 后端（课程目标）

目标：在 Apple Silicon 上用自己的代码生成器替代 LLVM，直接输出 ARM64 汇编。

策略：ARM64 平台使用自研后端，其他平台保留 LLVM 后端作为 fallback。运行时检测平台自动切换：

```text
四元式 ──┬── platform = arm64  → codegen_arm64.py → .s → gcc → 可执行
         └── platform = other  → codegen_llvm.py  → .ll → clang → 可执行
```

任务：

- 设计 `codegen_arm64.py` 整体结构
- 实现栈帧管理（局部变量栈偏移计算）
- 实现指令选择（四元式 → ARM64 指令映射）
- 实现控制流（if/else、while → 条件跳转标签）
- 实现函数调用（遵守 AAPCS64 调用约定、参数传递、返回值）
- 实现运行时函数调用（通过 `bl _printf` 等调用 C 标准库）
- 改造 `neko.py` 中的 `compile_to_executable`，加入平台判断与 gcc 链接
- 补充 ARM64 后端的端到端测试

完成标准：

- 所有示例程序和测试用例在 ARM64 后端下编译运行通过
- LLVM 后端保留，其他平台不受影响

## v0.1 建议范围

建议将首个明确版本控制在以下范围内：

- 类型：`int`、`float`、`char`、`bool`
- 语句：变量声明、赋值、条件、循环、函数、返回、输出
- 数据结构：一维数组
- 后端：生成 LLVM IR，并通过 `clang` 链接成可执行文件（ARM64 平台可使用自研后端）
- 运行时：输出、命令行参数、基础文件读写
- 工具链：统一 CLI 命令入口

## 后续规划与优先级

以下方向按优先级排列。P0 优先实现，为后续开发提供更好的调试和迭代体验。

### P0：简易项目工具（提升开发效率）

依赖：无。

当前每次编译都要手动指定 `.neko` 文件路径，调试多文件项目不方便。先做一个最小可用的项目工具，让日常开发更顺畅：

- `Neko.toml` 最小项目清单（项目名、入口文件）
- `nekgo new <name>` 生成项目骨架（创建目录 + Neko.toml + main.neko 模板）
- `nekgo build` 自动读取 Neko.toml 编译项目
- `nekgo run` 编译并运行
- 不需要多文件编译、依赖管理，只做单文件项目的脚手架

完成标准：

- `nekgo new demo && cd demo && nekgo run` 一键跑通
- 不再需要手敲完整文件路径

当前状态：已完成

### P1：自研 ARM64 后端（课程目标）

依赖：P0 完成后即可开始。

详见 Phase 7。核心是把四元式翻译为 ARM64 汇编，在 Apple Silicon 上独立于 LLVM 编译运行。P0 的项目工具可以让 ARM64 后端的开发调试更方便。

### P2：外部函数声明（`extern`）

依赖：无，可与 P0/P1 并行。

当前所有 C 运行时函数（`nekoprint_int`、`neko_argv_int` 等）硬编码在编译器内部。引入 `extern` 后，用户可在 `.neko` 源码中声明任意 C 函数：

```scheme
(extern printf ((string) int))
(extern sin ((float) float))
(extern malloc ((int) pointer))
```

语义分析阶段将 extern 注册到符号表，代码生成时按 C 调用约定生成调用指令。这使语言可扩展性强得多，也为后续链接用户自定义 C 库打下基础。

### P3：多文件编译与模块系统

依赖：P2（extern）。

当前只能编译单个 `.neko` 文件。项目稍大就需要拆分文件：

- 支持 `import` 其他 `.neko` 文件的函数和变量
- 名称修饰（name mangling）避免跨模块同名冲突
- 编译器遍历依赖图，分别生成目标文件，最终链接

这是包管理器的前提条件——没有多文件编译，依赖包无法被引用。

### P4：完整项目工具

依赖：P3（多文件编译）。

在 P0 简易版基础上扩展：

- 项目级多文件构建（自动扫描 `src/` 目录）
- `nekgo test` 运行测试
- `nekgo clean` 清理构建产物
- 构建模式：`debug` / `release`

### P5：包管理器

依赖：P4（完整项目工具）。

类 Cargo 的包管理与依赖管理：

- 包注册表（托管服务 + API）
- `nekgo add <pkg>` 从注册表下载依赖
- 语义化版本（semver）与依赖解析算法
- `Neko.toml` 中的 `[dependencies]` 声明
- 锁文件（`Neko.lock`）保证可复现构建
- 本地路径依赖（开发阶段用）

### P6：高级语言特性（远期）

依赖：P3 之后。

这些特性提升语言表达力，但不阻塞工具链：

- **宏系统**：编译期代码生成 / 语法扩展
- **结构体 / 记录类型**：自定义复合数据结构
- **字符串操作**：拼接、切片、格式化
- **标准库**：常用数据结构（链表、哈希表）和算法

### 延后方向

以下方向当前不进入路线，记录备忘：

- 解释执行 / REPL
- 垃圾回收
- 高级优化器（内联、循环优化、逃逸分析）
- 并发 / 异步
- 跨平台 x86-64 后端（当前由 LLVM 后端覆盖）
